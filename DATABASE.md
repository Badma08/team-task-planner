# DATABASE.md

## Назначение документа

Этот документ описывает будущую модель данных MVP. Базу данных не нужно подключать, пока отдельная задача явно не просит это сделать.

## База данных

Планируемый стек:

- Supabase
- PostgreSQL

## Главное правило данных

Все командные данные должны быть связаны с `team_id`. Это касается проектов, задач, участников и других сущностей, которые принадлежат команде.

## Основные сущности

### users

Пользователь приложения.

Поля-кандидаты:

- `id`
- `email`
- `name`
- `avatar_url`
- `created_at`

### teams

Команда, внутри которой ведется планирование.

Поля-кандидаты:

- `id`
- `name`
- `created_at`

### team_members

Связь пользователя с командой.

Поля-кандидаты:

- `id`
- `team_id`
- `user_id`
- `role`
- `created_at`

### projects

Проект команды.

Поля-кандидаты:

- `id`
- `team_id`
- `name`
- `description`
- `created_at`
- `updated_at`

### tasks

Задача внутри команды и, при необходимости, проекта.

Поля-кандидаты:

- `id`
- `team_id`
- `project_id`
- `assignee_id`
- `title`
- `description`
- `status`
- `priority`
- `due_date`
- `created_at`
- `updated_at`

Статусы задач:

- `новая`
- `в работе`
- `на проверке`
- `готово`

Приоритеты задач:

- `низкий`
- `средний`
- `высокий`
- `срочно`

### comments

Комментарий к задаче.

Поля-кандидаты:

- `id`
- `team_id`
- `task_id`
- `author_id`
- `body`
- `created_at`
- `updated_at`

## Связи

- Один пользователь может быть участником нескольких команд.
- Одна команда имеет много участников.
- Одна команда имеет много проектов.
- Один проект имеет много задач.
- Одна задача может иметь одного исполнителя.
- Одна задача имеет много комментариев.
- Комментарий всегда принадлежит задаче и команде.

## Правила для будущих миграций

- Не создавать таблицы без явной задачи на подключение базы данных.
- Для командных таблиц всегда добавлять `team_id`.
- Для календаря использовать `tasks.due_date`.
- Для статусов и приоритетов использовать единые значения из этого документа.
